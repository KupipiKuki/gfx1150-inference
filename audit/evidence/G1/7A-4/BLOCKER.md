# BLOCKER-7A4-1 — the GGUF parser recurses on nested metadata arrays

**Status:** open. **Found by:** Phase 7A-4 (deterministic GGUF fuzz).
**Filed:** 2026-11-04. **Branch:** `wp/7A-4-fuzz`.
**Not fixed here:** Phase 7A-4 does not touch `src/`. The fix is a new work
package.

---

## 1. The defect

`GGUFParser` reads a metadata array by reading its element type and then
reading that many values *of that element type*
(`src/gguf_parser.py`, `_read_value`):

```python
if vtype == GGUFValueType.ARRAY:
    elem_type, count = self._read_fmt("<IQ")
    remaining = len(self._buf) - self._pos
    if count > remaining:
        raise ValueError(...)
    return [self._read_value(elem_type) for _ in range(count)]
```

Nothing checks that `elem_type` is a scalar, so an array whose element type is
itself `ARRAY` is read by **recursion**, one level per nesting. The GGUF format
does not allow a nested array, so the parser has to *reject* such a file; it
does not. It recurses until the interpreter's stack is exhausted and then
raises `RecursionError` — an exception the parser's contract does not include.

The documented failure mode of the parser is `ValueError` (every format problem
in `_parse` raises one). `RecursionError` is neither.

## 2. The minimized example

Hypothesis' `find` reports the threshold as *flaky*, because the depth at which
the stack runs out depends on the caller's own stack depth. Measured at a fixed
stack depth, with the default recursion limit of 1000:

| nesting depth | result |
|---|---|
| 990 | parsed |
| 991 | parsed |
| **992** | **RecursionError** |
| 993 | RecursionError |

* the minimized example is **11 962 bytes** (58 bytes of header plus 12 bytes
  per nesting level);
* its sha256 is
  `28fe58bf8fee9e0d9e0987b3cc2e09922ffb968f9f8809de34c7305d086bbebb`;
* it is generated by `tests/test_fuzz_gguf.py::_nested_array_header`, and the
  pinned test
  `test_nested_arrays_are_rejected_with_a_value_error` reproduces it.

So a hostile header of about **12 KiB** — an ordinary file size — makes the
parser raise an exception it does not document.

## 3. Why it matters

1. **The contract is broken.** A caller that catches `ValueError` — which is
   what the parser's own documentation and every caller in this repository do
   — does not catch `RecursionError`. The malformed file escapes as an
   unexpected exception.
2. **It is a stack-exhaustion path.** The parser's work is proportional to the
   input, but here the *interpreter's* stack is the limit: the depth is chosen
   by the attacker, not by the file size. A server that parses untrusted
   models has an unbounded-recursion path in front of it.
3. **The parser also accepts invalid files.** At a depth below the threshold
   (300 levels, 3.6 KiB) the nested array is **accepted** as if it were
   well formed, so the parser does not enforce the format rule at all.

## 4. The proposed fix (a new work package — not 7A-4)

The minimal, format-correct fix is to reject the invalid input at the point
where it is read:

```python
if vtype == GGUFValueType.ARRAY:
    elem_type, count = self._read_fmt("<IQ")
    if elem_type == GGUFValueType.ARRAY:
        raise ValueError("GGUF array element type must not be an array")
    ...
```

A recursion-depth limit would be a second line of defence, but it is not
needed once the invalid element type is rejected: the depth of a *valid* file
is bounded by the format.

Either way the fix belongs in `src/`, which Phase 7A-4 must not touch. The
pinned test in `tests/test_fuzz_gguf.py` is the acceptance criterion for the
fix: it asserts the documented behaviour (`ValueError`), so it fails today and
passes when the defect is fixed. It is a **strict** xfail, so the suite fails
if the test starts passing while the xfail is still in place — the fix cannot
land unnoticed.

## 5. What 7A-4 does about it

* The defect is **pinned** in the test suite (a strict xfail) with this
  report as its reference.
* The fuzz's own space keeps to the GGUF format's rule that an array's
  element type is a scalar, so the fuzz's contract — *any unhandled exception
  is a failure* — is not weakened. The nested-array class is covered by the
  dedicated test instead, where the current behaviour is stated exactly.
* The evidence bundle records the minimisation, the threshold and the
  mechanism (`fuzz.log`, `notes.md`).

## 6. Impact on the gate

The G1 item 7A-4 asks for "executable evidence that malformed GGUF headers
cannot crash the parser". This package delivers that evidence and it is
*negative* in one respect: a malformed header **can** crash the parser, in one
specific way, and the crash is now pinned and reported rather than
undocumented. G1 should treat the parser as **not yet fail-closed** until
BLOCKER-7A4-1 is fixed in a new package.
