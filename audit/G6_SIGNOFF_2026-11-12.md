## 3. Accepted scope (the honest release statement)

**Release scope:** text-only **llama-family** GGUFs whose **kernel paths are
hardware-verified on synthetic GGUFs** on the gfx1150 lanes (`Q4_0`/`Q4_K`/
`Q8_0`). This is **not** a real-GGUF golden: no real `Q4_0`/`Q4_K`/`Q8_0` file
has been compared against a reference, and **no real-GGUF flavor passes an
exact golden** (ledger ID 31, PARTIAL).

The real-GGUF evidence that does exist (llama-family `Q4_K_M`/`Q6_K` vs pinned
llama.cpp) is recorded with its measured outcome: tokenization reference-exact
after the SPM fix, greedy chains token-identical through every decisive step,
forking only at near-tie steps — strict 16-step **FAIL**, recorded, not
explained away. `Q4_K_M` remains **PARTIAL**; `Q6_K` tensor support remains
**VERIFIED** on the G0 synthetic-kernel evidence.

`phi3`/`gemma`: synthetic-fixture verified only — **not** in the release
scope. `qwen2`: **NOT YET**. Chat-template handling: **not** verified
end-to-end. 70B: never run. 8-hour endurance: never measured. Throughput:
recorded as benchmark medians/p95 with a regression gate, **not** published as
a product claim.

## 4. Carry-forwards (non-blocking, tracked)

- **G6-QF-1 — CPU residency probe flake.** `test_measured_rss_delta_pin_vs_stream`
  failed once on a GitHub-hosted runner (`refault majflt=0` — the page cache
  retained the synthetic file) and passed on rerun **with no code change**.
  `fadvise(DONTNEED)` is best-effort and the fixture is never `fsync`ed.
  Harden in 7G (fsync the fixture; fall back from a failed `MADV_PAGEOUT` to
  `MADV_DONTNEED`; or a documented skip when the kernel retains pages). The 7D
  claim is explicitly best-effort — no claim changes.
- **G6-QF-2 — runner registration fragility.** The server-side registration was
  deleted once while the local credentials stayed stale, which left the
  required GPU check queueing. The host also reboots daily (~03:38 UTC), after
  the 03:00 UTC nightly cron. Document the re-registration procedure
  (`PHASE7_7F1_RUNNER_RUNBOOK.md` §10) and align the cron with the boot
  window, or keep the machine awake.
- **G6-QF-4 — required GPU check vs. push-only workflows.** The ruleset
  requires `GPU correctness (self-hosted gfx1150)` on `main` and
  `vibe/phase7-220201`, but `ci-gpu.yml` triggers only on `pull_request`,
  `schedule` and `workflow_dispatch` — never on `push`. A direct push to a
  protected branch therefore cannot satisfy the rule until the four checks have
  already been reported **for that exact SHA**, which for the GPU lane only
  happens once a PR contains it (observed live: the push of `d984d79` was
  declined with `4 of 4 required status checks are expected`, and `a93da85`
  could not be pushed to `vibe/phase7-220201` for the same reason). Either
  add a `push` trigger to the GPU lane, or route protected-branch changes
  through PRs (the current practice).
- **G6-QF-3 — thin decisive-margin evidence.** The only decisive-margin pass
  covers two steps. A future evidence package should use prompts whose first
  steps are decisive, or require a minimum number of decisive steps, so the
  real-GGUF evidence is stronger.
