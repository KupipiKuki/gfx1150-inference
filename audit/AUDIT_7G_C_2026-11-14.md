## 3. Blockers

### BLOCKER-7G-C-1 (High) — the watchdog cannot tell a healthy runner from a broken one

`runner_online()` decides health with:

```bash
journalctl -u "${SERVICE_UNIT}" --since "-10 min" --no-pager \
  | grep -q "${LISTEN_MARKER}"          # LISTEN_MARKER="Listening for Jobs"
```

`Listening for Jobs` is a **startup-only** marker. From this host's journal:

| marker occurrences | service starts |
|---|---|
| **3** | **8** |

Proof from the journal: the runner was **online and working** at Nov 12 23:20
(it ran PR #8's GPU job at 23:33; the service had been up since 22:50), and the
marker inside a 10-minute window ending then is **0 hits** — the marker was 30
minutes old.

Consequences with the shipped timer (`OnUnitActiveSec=5min`):

- **with the PAT deployed:** the watchdog concludes "offline" every 5 minutes
  and **re-registers and restarts the runner every 5 minutes** — churn that can
  interrupt a running job (a `config.sh --replace` replaces the registration
  and the service is restarted);
- **without the PAT:** the run dies at "PAT file not readable", the
  `OnFailure` alert fires **every 5 minutes**, and a real outage is
  indistinguishable from the noise.

So C2's acceptance criterion ("a simulated deletion-and-recovery brings the
runner back by itself") is **not met**: the watchdog never recognises the
healthy state it is meant to preserve.

**Required fix (health check).** Decide health from the *current* runner
process and the *current* registration, not from a startup marker:

```bash
runner_online() {
  systemctl is-active --quiet "${SERVICE_UNIT}" || return 1
  # the listener process for the *current* service start must be alive
  systemctl show "${SERVICE_UNIT}" -p ActiveState -p SubState --value \
    | grep -q '^active$' || return 1
  pgrep -u "${SERVICE_USER}" -f 'Runner\.Listener' >/dev/null || return 1
  # and the newest diag log of the current start must not show a dead registration
  newest="$(ls -t "${RUNNER_DIR}"/_diag/Runner_*.log 2>/dev/null | head -1)"
  [ -n "${newest}" ] || return 1
  grep -q "${LISTEN_MARKER}" "${newest}" || return 1
  ! grep -q "registration has been deleted" "${newest}" || return 1
  return 0
}
```

(equivalently: parse the service's start time and search the journal from
that time — the point is to stop using a *moving* time window for a
*startup-only* marker).

**Required fix (repair discipline).** A repair must not run while a job is
running, and must be rate-limited:

- skip the repair when a `Runner.Worker` process exists (a job is in flight);
- keep a cooldown (e.g. no more than one repair attempt per 30 minutes) so a
  persistent failure cannot loop;
- log every attempt with its outcome (already done) and exit non-zero on
  failure (already done).

**Acceptance:** with the runner healthy and up for more than ten minutes,
`ensure_runner_registered.sh --check` exits **0** and performs no repair;
with the registration deleted, the script performs exactly **one** repair and
then reports healthy. The QAQC's "watchdog brings runner back" check must be
re-run against a *real* healthy runner (not a fake `systemctl`), i.e. the
simulated-deletion transcript must include the healthy-state case.

### BLOCKER-7G-C-2 (Medium) — the repo-admin PAT is passed in `curl`'s argv

The script's header states:

> "the PAT is consumed by curl via a private fd redirection and never appears
> in argv"

and the brief requires:

> "The PAT is never in the repository, in a log, in a workflow file, in the
> service environment, or in the process list."

The implementation does the opposite:

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${PAT}" \
  ...
```

`-H "Authorization: Bearer ${PAT}"` is an **argv element**: any local user or
process can read `/proc/<pid>/cmdline` for the lifetime of the request (and
the journal/`ps` snapshot if the shell is traced). The QAQC adversarial check
"PAT never in process list → PASS (code review)" is therefore **incorrect** —
this audit corrects it: the PAT **does** appear in the process list.

**Required fix.** Keep the header out of argv (curl ≥ 7.55 supports `-H @file`
and `-K/--config`):

```bash
hdr="$(mktemp /root/.runner-hdr.XXXXXX)"; chmod 600 "${hdr}"
printf 'header = "Authorization: Bearer %s"\n' "${PAT}" > "${hdr}"
trap 'rm -f "${hdr}"' EXIT
curl -fsS -X POST -K "${hdr}" -H "Accept: application/vnd.github+json" \
  -o "${TOKEN_JSON}" "https://api.github.com/repos/${OWNER}/${REPO}/actions/runners/registration-token"
```

and unset the shell variable right after use.

**Also correct the comment** about the *registration* token: it is passed to
`config.sh --token` in argv **as the `kupipi` user** (`runuser -u`), so it is
readable in `/proc/<pid>/cmdline` by any local user for the ~1 s the call
takes — it is not a "root-only /proc slot". That token is short-lived and
single-use and grants only runner registration (low severity), but the
comment must state it accurately.

**Acceptance:** `ps -eo args` during a repair shows no PAT; the token window
is documented accurately; the evidence records a live repair (after the
owner deploys the PAT).

## 3a. Addendum (2026-11-14, post-fix verification) — a third C2 defect

The C2 remediation (`06ae6bc`, `3055097`) fixes BLOCKER-7G-C-1's *health
decision* and BLOCKER-7G-C-2's *argv exposure* correctly. Verification on the
live host uncovered one more defect in the **file selection**:

`runner_online()` picks the *newest* `_diag/Runner_*.log` **by mtime**. This
host suspends/resumes and its **wall clock jumps**, so mtimes are not ordered
by session: the current session's log is
`Runner_20261114-200156-utc.log` (service start 15:01:56 EST = 20:01:56 UTC,
which logged `Listening for Jobs` at 20:01:57Z), while a **stale log from the
previous boot** (`Runner_20261114-220338-utc.log`, containing
"registration has been deleted") carries a *future* mtime (`Nov 14 17:03`) and
therefore wins the "newest" comparison.

Effect: the watchdog reports **offline** for a perfectly healthy runner, the
`OnFailure` alert fires every 5 minutes, and the verdict stays wrong (the
cooldown prevents repair churn, so nothing is damaged — but the watchdog is
useless and noisy). Measured on the host right now: the runner **is** listening
(`journalctl` shows `Listening for Jobs` for the current session, and no
deletion after it), while `ensure_runner_registered.sh --check` exits 1.

**BLOCKER-7G-C-3 (Medium):** decide health from the **journal order**, never
from file mtimes (and never from `--since <ExecMainStartTimestamp>`, whose
timestamp is subject to the same clock jump):

```bash
runner_online() {
  systemctl is-active --quiet "${SERVICE_UNIT}" || return 1
  local svc_state
  svc_state="$(systemctl show "${SERVICE_UNIT}" -p ActiveState -p SubState --value 2>/dev/null || true)"
  grep -q '^active$' <<<"${svc_state}" || return 1
  pgrep -u "${SERVICE_USER}" -f 'Runner\.Listener' >/dev/null || return 1
  # JOURNAL ORDER, not mtimes and not a moving window: this host's clock
  # jumps after a suspend/resume, which reorders the _diag files by mtime.
  local jout last_listen last_del
  jout="$(journalctl -u "${SERVICE_UNIT}" --no-pager -o cat 2>/dev/null || true)"
  last_listen="$(grep -n "${LISTEN_MARKER}" <<<"${jout}" | tail -1 | cut -d: -f1)"
  last_del="$(grep -n "registration has been deleted" <<<"${jout}" | tail -1 | cut -d: -f1)"
  [ -n "${last_listen}" ] || return 1
  [ -z "${last_del}" ] || [ "${last_listen}" -gt "${last_del}" ] || return 1
  return 0
}
```

Verified against the live journal on this host: last `Listening for Jobs` at
journal line 156, last `registration has been deleted` at line 145 → **HEALTHY**
(correct verdict; the shipped check says offline).

**Also still open:** the PAT is **not deployed** (`/etc/gfx1150-runner` does
not exist), so the repair path cannot run at all and the alert noise is
guaranteed while the verdict is wrong. The PAT must be deployed only after
BLOCKER-7G-C-3 is fixed.

## 3b. Second addendum (2026-11-14) — ROOT CAUSE of the recurring "registration deleted": the **host clock**

While verifying the runner live (a dispatched GPU job stayed "Waiting for a
runner"), the true cause of every "the runner registration has been deleted
from the server" episode in this project was identified. It is **not** GitHub
deleting the registration:

```
timedatectl → "RTC in local TZ: yes"          ← the RTC holds LOCAL time
kernel: rtc_cmos PNP0B00:00: setting system clock to 2026-11-1xT..:..:.. UTC   (every boot)
systemd-resolved: Clock change detected. Flushing caches.                       (NTP steps it back)
```

At every boot/resume the kernel sets the **system clock from the RTC as if it
were UTC** → the clock jumps **+5 h** (the EST offset) → NTP then steps it
back. Inside that window the runner's broker handshake fails with a **clock
skew** error, which the runner reports with a misleading message:

```
7 runner logs contain:
  "The token is not valid until 11/11/2026 03:40:47. Current server time is 11/10/2026 22:40:22."
     → the runner's clock is 5 h ahead of GitHub's
```

and then:

```
"Failed to create a session. The runner registration has been deleted from the
 server, please re-configure."     ← the runner's interpretation of the skew error
```

So the recurring "registration deleted" was a **misdiagnosis of a clock-skew
rejection**. Consequences for this project:

1. Every re-registration performed **inside a skewed window** fails the same
   way, so "just re-register" never sticks.
2. The **C2 self-repair (PAT) cannot work** while the clock jumps: it would
   mint a token and re-register inside the skewed window and fail again. The
   clock fix is therefore a **prerequisite** for C2, not an optional extra.
3. The watchdog's health check must distinguish **CLOCK-SKEW** from a deleted
   registration (the diag log contains "not valid until" for the skew case).

**Required (host):** keep the RTC in UTC and make the correction smooth.

```bash
sudo timedatectl set-local-rtc 0          # RTC in UTC: no +5 h jump at boot
sudo apt install -y chrony                 # or keep systemd-timesyncd
# /etc/chrony/chrony.conf:  makestep 1.0 3   rtcsync   pool time.cloudflare.com iburst
sudo systemctl enable --now chrony
```

**Required (watchdog):** a skew guard, before any repair attempt:

```bash
skew_guard() {
  local host gh
  host="$(date -u +%s)"
  gh="$(curl -fsSI --max-time 10 https://api.github.com 2>/dev/null         | grep -i '^date:' | sed 's/^date: //' | xargs -I{} date -u -d '{}' +%s)" || return 0
  [ -n "${gh}" ] || return 0
  [ $(( host - gh )) -lt -60 ] || [ $(( host - gh )) -gt 60 ] || return 0
  log "CLOCK-SKEW: host is $(( host - gh ))s from GitHub — the runner session will be rejected; fix timekeeping first"
  return 1
}
```

and, after a repair, assert the agent's labels still include `gfx1150` and
`rocm` (the workflow's `runs-on` set), so a label regression is caught rather
than silently queuing jobs forever.
